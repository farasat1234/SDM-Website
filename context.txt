====================================================================
1. WHAT THIS PROJECT IS
====================================================================
Business/marketing website for "System Dies and Mould" (SDM), a precision
manufacturing company based in Karachi, Pakistan (dies, press tools,
injection/blow moulds, FRP/GRP fabrication, CNC machining, jigs & fixtures,
reverse engineering, EV parts, etc.).

It is a two-tier app:
  - frontend/  → Next.js 14 (React 18) marketing site — multi-page, mostly
                 static content, image galleries, a contact form, and a
                 simple rule-based chatbot widget.
  - backend/   → Node.js + Express API — handles the contact form (email via
                 Nodemailer/Gmail SMTP), the chatbot's keyword-matching
                 replies (also emails a lead summary), and serves a scanned
                 listing of project photos from the filesystem.

There is no database. State is not persisted anywhere except by emailing
form/chat submissions to the company inbox. No user auth, no CMS — content
is hardcoded in React components and page files, and images are static
files under frontend/public/.

Backend:
  - Node.js + Express (no framework version pinned, uses "*" in package.json —
    should pin versions before deploying to prod)
  - cors, body-parser, dotenv
  - multer (in-memory storage) for handling file attachments on the contact form
  - nodemailer for sending email via Gmail SMTP (app password based, not OAuth)
  - nodemon for dev auto-restart

No TypeScript anywhere (plain .js/.jsx). No test suite present. No CI config
found in the repo root.

4. HOW THE PIECES CONNECT (RUNTIME FLOW)
====================================================================
1. Browser loads Next.js frontend (localhost:3000 in dev).
2. Static marketing content renders directly from React components — no
   frontend calls needed for most of the page.
3. Contact form (Contact.jsx) → POST {BACKEND_URL}/api/contact (multipart/
   form-data with optional file) → backend validates → nodemailer sends a
   formatted HTML email to FEEDBACK_EMAIL, replyTo set to the visitor's email.
4. ChatBot widget (ChatBot.jsx) → POST {BACKEND_URL}/api/chat with
   { message } → backend matches keywords in chatService.js, returns
   { reply } immediately, and separately (async, non-blocking) emails a lead
   summary of the exchange to FEEDBACK_EMAIL.
5. WhatsApp button is a plain external link (wa.me), no backend involvement.
6. Backend has a GET /api/projects style endpoint (routes/projects.js) meant
   to scan the public/OurProjects folder and return image metadata as JSON,
   but IT IS NOT WIRED UP in server.js — confirm intended usage before
   assuming the frontend gallery is dynamic; likely the gallery components
   (OurProjects.jsx / Projects.jsx) hardcode paths instead.

Frontend and backend are two separate processes/servers (ports 3000 and
5000 by default) — there is no server-side rendering that calls the backend
at build time; all backend calls are client-side (axios in the browser).

7. DEPLOYMENT CONSIDERATIONS / KNOWN ISSUES TO FLAG
====================================================================
- Two independently deployable services: frontend (Next.js — deploy to
  Vercel/Node host) and backend (Express — deploy to Render/Railway/EC2/etc.
  or as a Node service). They are NOT a monorepo with shared build; no
  Docker/CI config present in repo.
- CORS on backend is locked to a single FRONTEND_URL origin — must be set
  correctly per environment (dev vs prod) or contact/chat calls will fail
  cross-origin in production.
- backend/package.json pins dependencies with "*" (latest) instead of exact/
  caret versions for express, cors, dotenv, body-parser, nodemailer — should
  be pinned before a reproducible production deploy.
- routes/projects.js is unused/unmounted in server.js — confirm whether the
  gallery is meant to be dynamic (via this endpoint) or fully static before
  deploying; also fix the "ourprojects" vs "OurProjects" case mismatch if
  deploying to a case-sensitive filesystem (Linux).
- SMTP auth uses a Gmail App Password — fine for low volume, but consider a
  transactional email provider (SendGrid/SES/Postmark) for reliability at
  scale/production, since Gmail SMTP has sending limits and can be flagged.
- No .env files should ever be committed — confirm .gitignore covers both
  backend/.env and frontend/.env.local (frontend currently has a .gitignore
  but no .env.local.example was found — add one for onboarding parity with
  backend/.env.example).
- Static image assets total ~239 MB under frontend/public — this bloats the
  repo and slow deploys/builds; consider moving to a CDN/object storage
  (S3/Cloudinary) and referencing via URL instead of shipping in the Next.js
  build, especially if deploying frontend to a platform with build-size limits.
- No automated tests, no TypeScript, no linting config visible at the repo
  root — verify code correctness manually / add basic checks before major
  changes.
- Chatbot is fully rule-based (keyword matching in chatService.js) — it is
  NOT calling any AI/LLM API. If asked to "improve the chatbot," clarify
  whether the goal is to keep it rule-based or integrate an actual LLM.
